Vamos começar pela arquitetura geral do sistema. Temos um SoC baseado em LiteX com um core VexRiscv RV32IMA a 50 MHz e a NPU v2 conectada via Wishbone.

A comunicação acontece em dois níveis: primeiro, a CPU configura a NPU escrevendo nos registradores via Wishbone Slave — endereço das ativações, endereço de destino, e o start. Depois, a NPU assume o controle do barramento como Wishbone Master e faz leituras burst da RAM para carregar ativações e pesos.

Importante notar que a NPU é intencionalmente simples: ela só faz o produto interno MAC ternário utilizando 64 MACs em paralelo. Todo o resto — BatchNorm, ReLU, quantização, e a camada de saída FP32 — fica por conta da CPU.

Ao final de cada camada, a NPU gera uma IRQ pela linha 10 do PLIC, e a CPU acorda para processar os resultados.

Vamos detalhar o layout da memória compartilhada entre CPU e NPU. O buffer DMA tem 4 MB mapeados a partir do endereço físico 0x80000000.

A organização é a seguinte: os primeiros 1024 bytes são reservados para as ativações da camada atual. A CPU escreve a imagem MNIST aqui antes de iniciar a Layer 0, e depois reescreve com as ativações processadas antes de cada camada subsequente.

Os pesos ficam em três regiões distintas: Layer 0 em 0x1000 (200 KB), Layer 1 em 0x32000 (131 KB), Layer 2 em 0x52000 (32 KB).

Já os resultados de cada camada são escritos pela NPU em regiões separadas — 0x5C000, 0x5D000 e 0x5D800 — permitindo que a CPU leia os resultados de uma camada enquanto prepara a próxima.

Reparem que tudo depende de cur_layer: as fórmulas de endereçamento no RTL usam cur_layer para indexar os vetores layer_in, layer_out, layer_wcnt, e para calcular o offset dos pesos. Se cur_layer estiver errado, tudo desanda.

Os pesos ternários são codificados em apenas 2 bits cada, com uma representação inteligente: 01 para +1, 00 para 0, e 11 para -1. Note que não usamos 10 — isso permite detectar erros.

Cada palavra de 32 bits armazena 16 pesos consecutivos em little-endian. Por exemplo, 0x55555555 representa 16 pesos +1.

A matriz de pesos é organizada por neurônio. Para a Layer 0, cada neurônio tem 49 words de peso (porque 784 ativações ÷ 16 pesos por word = 49). Os batches de 64 ativações são processados 4 words por vez.

A tabela de operações mostra a escala: a Layer 0 faz ~852 mil MACs em ~60 mil ciclos, tudo sem multiplicadores — apenas somas e subtrações. A NPU faz isso sem intervenção do CPU.

Esta é a essência da NPU: zero DSPs, puramente lógica combinacional. Cada MAC é simplesmente um multiplexador que escolhe entre somar, subtrair ou pular, dependendo do peso ternário.

O código RTL mostra o loop paralelo: 64 MACs executam em um único ciclo. Cada MAC pega uma ativação diferente de act_mem e um peso diferente de wt_buf, e o resultado é acumulado em acc_reg[0].

As ativações vêm em batches de 64. A wt_buf carrega 4 words (64 pesos) por vez via DMA. Para cada batch, a NPU faz um ciclo de load (4 words da RAM) seguido de um ciclo de accumulate (64 MACs).

Para a Layer 0: 49 batches por neurônio × 1024 neurônios = 50.176 loads e 50.176 accumulates. Cada neurônio gera um int32 que é escrito na RAM. A economia de não ter multiplicadores é enorme em área e potência.

Vamos examinar a FSM estado a estado. Este é o coração do controle da NPU. Começamos pelos primeiros três estados.

No estado IDLE, a NPU fica esperando o comando start vindo da CPU. Quando cmd_start é recebido, ela zera os registradores de controle — incluindo cur_layer. É aqui que mora o bug: cada nova invocação reseta cur_layer para 0, Independentemente de qual camada deveria ser processada.

No CFG_ACT, a NPU configura o DMA para ler as ativações da RAM. O endereço é calculado como cfg_src_addr + cur_layer * 1024, e o número de bytes é layer_in[cur_layer].

No DMA_ACT, cada palavra de 32 bits vinda da RAM é desmembrada em 4 bytes individuais e armazenada em act_mem. Como as ativações são uint8, cada palavra carrega 4 ativações. Quando act_waddr atinge layer_in[cur_layer], a FSM avança para COMPUTE_BATCH.

Agora os estados de computação e finalização. No COMPUTE_BATCH, a NPU alterna entre dois sub-estados: LOAD_WEIGHTS e ACCUMULATE.

No LOAD_WEIGHTS, o DMA lê 4 words (64 pesos) da RAM. O endereço é calculado com base no neurônio atual (cur_output), no batch atual (cur_in_batch), e no words_per_output da camada.

No ACCUMULATE, os 64 MACs disparam em paralelo por um ciclo, cada um processando uma ativação e um peso diferentes. Se é o último batch do neurônio, a FSM vai para WRITE_RESULT.

O WRITE_RESULT escreve o acumulador de 32 bits na RAM de resultados, e o NEXT_OUTPUT prepara o próximo neurônio. Quando todos os neurônios da camada são processados, a FSM vai para LAYER_DONE, que decide se deve ir para DONE (com IRQ) ou NEXT_LAYER, dependendo de LAYER_CFG.

Toda vez que o CPU escreve CONTROL.start = 1, cur_layer volta para 0.

Diagrama de Consequências

┌─────────────────────┐ │ CPU: CONTROL.start │ └──────────┬──────────┘ │ ▼ ┌─────────────────────┐ │ IDLE: cur_layer=0 │◄── BUG! └──────────┬──────────┘ │ ┌──────────▼──────────┐ │ CFG_ACT: lê ativações│ │ de cfg_src_addr + 0 │ ← SEMPRE offset 0! └─────────────────────┘ │ ┌──────────▼──────────┐ │ COMPUTE: pesos de │ │ cfg_src + 4096 + 0 │ ← SEMPRE layer 0! └─────────────────────┘

Aqui está o bug central que motivou toda esta análise. Na linha 248-249 do RTL, quando a FSM está em IDLE e recebe cmd_start, ela zera cur_layer — sempre.

Isso significa que não importa qual camada você queira processar: a NPU sempre vai achar que é a Layer 0. Ela vai ler ativações do offset 0, vai usar weights_per_output da Layer 0, e vai processar layer_out[0] neurônios.

O diagrama de consequências mostra o efeito domino: cur_layer=0 afeta o endereço das ativações (sempre cfg_src_addr + 0), o offset dos pesos (sempre o início dos pesos da Layer 0), e as dimensões (layer_in, layer_out, layer_wcnt todos indexados por cur_layer).

Este bug impede qualquer processamento multi-camada, seja com LAYER_CFG=1 (uma camada por start) ou LAYER_CFG=3 (três camadas em sequência).

Vamos analisar as consequências do bug nos dois modos de operação.

No modo LAYER_CFG=1 (processa uma camada e gera IRQ), a primeira invocação funciona porque cur_layer é 0 e a Layer 0 é processada corretamente. Mas na segunda invocação, cur_layer ainda é 0, então a NPU lê os pesos da Layer 0 em vez da Layer 1, usa 49 words_per_output em vez de 64, e processa 1024 neurônios em vez de 512. O resultado é completamente errado.

No modo LAYER_CFG=3 (processa 3 camadas automaticamente), o problema é diferente. cur_layer incrementa corretamente via NEXT_LAYER, mas as ativações vêm do lugar errado. A Layer 0 escreve resultados em cfg_dst_addr, mas a Layer 1 tenta ler ativações de cfg_src_addr + 1024 — que não é onde os resultados estão. O resultado é lixo matemático.

A última linha mostra que mesmo se configurássemos cfg_dst = cfg_src + offset, ainda teríamos um problema: os resultados são int32 mas o DMA lê como uint8.

Mínima modificação no RTL: adicionar seletor de camada manual no registrador LAYER_CTRL.

A correção proposta é minimalista: aproveitamos o registrador LAYER_CTRL existente (offset 0x2C) e adicionamos dois campos: layer_override_en (bit 8) e layer_override (bits 7:6).

Quando layer_override_en = 1, o valor de cur_layer no start vem do registrador em vez de ser zerado. Quando layer_override_en = 0, o comportamento é exatamente o original — compatibilidade total.

Os valores são simples: Layer 0 pode ser invocada sem override (0x000), Layer 1 com 0x140, Layer 2 com 0x180. O bit 0 (irq_per_layer) fica em 0 porque queremos IRQ ao fim de cada camada.

Com cur_layer correto, todas as dimensões e endereços são calculados adequadamente: layer_in, layer_out, layer_wcnt, words_per_output e layer_weight_offset. A tabela mostra que para a Layer 1, tudo passa a funcionar.

Com a correção aplicada, o fluxo funciona perfeitamente. A tabela mostra os três cenários: cada camada é invocada com LAYER_CFG=1 e o override apropriado. O SRC_ADDR é sempre o mesmo (as ativações estão sempre no offset 0), mas a NPU interpreta os dados corretamente porque cur_layer está certo.

O diagrama temporal mostra a alternância entre CPU e NPU: a CPU prepara a RAM, configura a NPU, e dorme. A NPU processa e emite IRQ. A CPU acorda, processa BatchNorm+ReLU+quant, reconfigura para a próxima camada, e dorme de novo. Três IRQs no total.

O importante é que a CPU fica em modo de baixo consumo entre as IRQs — o driver usa wait_event_interruptible, que permite ao kernel escalonar outros processos ou entrar em idle. Para um sistema embarcado, isso é essencial.

Com este fluxo, a inferência completa de uma imagem MNIST leva aproximadamente 110 mil ciclos de NPU mais o processamento da CPU entre as camadas.

NPU é intencionalmente simples — zero DSPs. Software faz o resto.

Um ponto crucial: a rede neural foi treinada com BatchNorm entre todas as camadas — é o que mostra o código Keras do train_qat_mnist.py. Cada camada ternária é seguida de BatchNormalization, ReLU e FakeQuant.

A NPU não pode fazer nada disso. Ela não tem multiplicadores FP32 (zero DSPs), não tem comparador para ReLU, e não tem conversor FP32→int8 para a quantização. A NPU foi projetada para ser minimalista: apenas o MAC ternário.

A fórmula do BatchNorm na inferência é determinística porque os parâmetros (γ, β, μ, σ²) são fixos do treino. É uma transformação linear y = A·x + B, mas com A e B diferentes para cada neurônio, o que inviabiliza a fusão com os pesos sem retreinar.

Por isso a CPU é essencial entre as camadas: ela lê os resultados int32 da NPU, aplica BatchNorm (float), ReLU (max), quantiza para [0,127] (uint8), e escreve de volta na RAM para a próxima camada.

O que a NPU tem / não tem

✅ 64 MACs ternários paralelos

Multiplierless: Mux + add/sub. Zero DSPs. 64 operações por ciclo.

✅ DMA autônomo (Wishbone Master)

Lê ativações e pesos da RAM, escreve resultados. CPU não介入 durante.

✅ Geração de IRQ

Sinaliza fim de camada via PLIC (linha 10). CPU dorme entre IRQs.

❌ Sem multiplicador FP32

Zero DSPs. Não pode fazer BatchNorm (γ·(x-μ)/σ + β).

❌ Sem comparador (ReLU)

Não pode fazer max(0, x). CPU faz ReLU via fmaxf().

❌ Sem conversão FP32→int8

Não pode fazer fake_quant. CPU faz clamp(round(x), 0, 127).

NPU = engine de MAC ternários. CPU = cérebro (BN + ReLU + quant + FP32).

Este slide resume de forma visual o que a NPU pode e não pode fazer. É uma distinção fundamental para entender a arquitetura do sistema.

A NPU é excelente no que foi projetada para fazer: 64 MACs ternários em paralelo, zero DSPs, com DMA autônomo e geração de IRQ. Ela processa centenas de milhares de MACs em dezenas de milhares de ciclos, sem intervenção do CPU.

Mas ela não tem recursos para operações FP32, comparação, ou conversão de formato. Isso é intencional — a NPU foi mantida simples para economizar área e consumo.

A divisão de trabalho é clara: a NPU faz o trabalho pesado (MACs), e a CPU faz o processamento inteligente entre as camadas. Esta é uma arquitetura híbrida hardware-software que equilibra performance e flexibilidade.

Vamos agora para a implementação em C do fluxo completo. Este slide mostra o setup inicial.

Primeiro, fazemos o mmap do buffer DMA de 4 MB. Este buffer é compartilhado entre CPU e NPU — ambos enxergam o mesmo espaço de endereçamento físico a partir de 0x80000000. Na prática, o driver do sistema faz este mapeamento e retorna o ponteiro.

A imagem MNIST de 784 bytes é copiada para o offset 0x0000, com normalização de [0,255] para [0,127]. Isso porque as ativações na NPU são uint8, e o treino QAT já considera esta escala.

Os pesos ternários são copiados para três regiões distintas da RAM: 0x1000, 0x32000 e 0x52000. Eles já vêm no formato de 2 bits por peso, empacotados em uint32. O mmap devolve um ponteiro virtual, mas o driver conhece o endereço físico que deve ser passado para a NPU via SRC_ADDR.

Layer 0 (784→1024)

Configuração da NPU

// SRC_ADDR = início das ativações
npu_write(NPU_BASE+0x08, dma_phys+0x0000);

// DST_ADDR = resultados Layer 0
npu_write(NPU_BASE+0x0C, dma_phys+0x5C000);

// LAYER_CFG = 1 (uma camada)
npu_write(NPU_BASE+0x24, 1);

// LAYER_CTRL = 0 (sem override)
npu_write(NPU_BASE+0x2C, 0x000);

// CONTROL.start = 1 → cur_layer=0
npu_write(NPU_BASE+0x04, 1);

Fluxo na NPU

NPU L0: act_mem ← dma+0x0000 (784 B) for j=0..1023: for b=0..12: wt_buf ← dma+0x1000 + j*49*4 + b*16 64 MACs → acc_reg[0] dma+0x5C000+j*4 ← acc_reg[0] IRQ!

CPU: BN + ReLU + Quant

int32_t *out = (int32_t*)(dma+0x5C000);
for (int j = 0; j < 1024; j++) {

            * (out[j] - bn_mean_0[j])
            / sqrtf(bn_var_0[j] + 1e-5f)
            + bn_beta_0[j];

    ((uint8_t*)dma)[j] =
        (uint8_t)fminf(fmaxf(y,0),127);
    // Ativações L1 em dma+0x0000
}

Aqui está o código completo da Layer 0. Primeiro, configuramos os registradores da NPU via Wishbone: SRC_ADDR aponta para o início do buffer (onde está a imagem), DST_ADDR para a região de resultados da Layer 0, LAYER_CFG=1 para processar uma camada e gerar IRQ, e LAYER_CTRL=0 porque não precisamos de override (cur_layer=0 é o comportamento padrão).

Ao escrever CONTROL.start=1, a NPU acorda do IDLE e começa o processamento. Ela carrega 784 bytes de ativação em act_mem, e para cada um dos 1024 neurônios, itera sobre 13 batches de 64 ativações, acumulando em acc_reg[0]. O resultado int32 de cada neurônio é escrito na RAM em dma+0x5C000.

Quando termina, a NPU gera IRQ. A CPU acorda e aplica BatchNorm + ReLU + quantização. Para cada um dos 1024 neurônios, a CPU calcula y = γ·(x-μ)/√(σ²+ε) + β, aplica ReLU (max com 0), e quantiza para uint8 em [0,127].

Importante: as ativações processadas são escritas de volta no offset 0x0000 da RAM — o mesmo lugar onde a imagem estava. Isso permite que a Layer 1 leia do mesmo SRC_ADDR.

Agora as camadas 1 e 2 com o override ativo. Notem a semelhança com a Layer 0: SRC_ADDR continua o mesmo (dma_phys+0x0000), DST_ADDR muda para as respectivas regiões de resultado, e LAYER_CTRL agora tem override=1 (0x140) para Layer 1 e override=2 (0x180) para Layer 2.

Para a Layer 1, a NPU lê 1024 bytes de ativação de dma+0x0000 — estes são os resultados processados da Layer 0 que a CPU escreveu. Ela processa 512 neurônios com 64 words por neurônio, lendo pesos de dma+0x32000. O resultado é escrito em dma+0x5D000.

Para a Layer 2, a NPU lê 512 bytes de ativação de dma+0x0000, processa 256 neurônios com 32 words por neurônio, pesos de dma+0x52000, e escreve em dma+0x5D800.

Em ambos os casos, a CPU aplica BatchNorm + ReLU + quant após a IRQ, com os parâmetros específicos de cada camada (bn_gamma/beta/mean/var_1 para Layer 1, _2 para Layer 2).

A última camada — o classificador — roda inteiramente na CPU. É uma Dense(256→10) com pesos FP32. O código é simples: para cada uma das 10 classes, calculamos o produto interno entre as 256 ativações da Layer 2 e os pesos da classe, somando o bias.

Para classificação MNIST, não precisamos da softmax — ela é monotônica, então o argmax nos dá a mesma classe. Isso economiza 10 exponenciações e uma divisão.

O diagrama da inferência completa mostra o fluxo inteiro: 3 passagens pela NPU (uma por camada ternária), cada uma seguida de processamento BN+ReLU+quant pela CPU, e finalmente a output layer na CPU.

No total, são 3 IRQs, aproximadamente 110 mil ciclos de NPU (somando as 3 camadas), e cerca de 1 milhão de operações de ponto flutuante na CPU entre BN e output layer. Para um sistema RV32IMA sem FPU hardware, isso pode levar alguns milhões de ciclos adicionais — mas ainda assim aceitável para inferência de uma imagem.

O mecanismo de IRQ é simples mas essencial. A NPU não tem acesso direto ao sistema de interrupções do RISC-V — ela vai para ST_DONE, asserta irq_out=1, e o PLIC (Platform-Level Interrupt Controller) do VexRiscv roteia essa interrupção como IRQ #10 para a CPU.

No lado do software, o driver usa wait_event_interruptible (ou equivalente no bare-metal) para dormir até a IRQ chegar. Quando a interrupção ocorre, a CPU lê os resultados da RAM compartilhada, processa BN+ReLU+quant, escreve CONTROL.bit1=1 para limpar a IRQ (isso faz a NPU voltar a IDLE), reconfigura os registradores para a próxima camada, e escreve CONTROL.bit0=1 para o próximo start.

A timeline mostra 3 IRQs no total, espaçadas por aproximadamente 40-60 mil ciclos de NPU mais o processamento da CPU. Assumindo que a CPU a 50 MHz processa os floats em alguns milhares de ciclos, a inferência completa leva menos de 5 milissegundos.

Importante: a CPU dorme entre as IRQs, o que minimiza o consumo em um sistema embarcado.

🔴 Inconsistência #3: Simulador C++ só salva o último grupo

RTL faz cur_output++ (1 por vez) e escreve cada resultado na RAM. Simulador processa 64 por vez e descarta intermediários. Não reflete o RTL.

Além do bug do cur_layer, encontrei três inconsistências no código do projeto que precisam ser corrigidas.

A primeira está no script Python que gera o weights.h. Ele filtra apenas as camadas QuantDense, ignorando completamente BatchNorm e a output layer FP32. Isso significa que o weights.h atual não tem os parâmetros γ, β, μ, σ² necessários para a HAL fazer BatchNorm, nem os pesos e biases da output layer. Sem isso, não é possível executar a inferência completa.

A segunda é no user_app.c — especificamente no modo CPU baseline. Ele faz um cast direto de int32_t* para uint8_t*, o que em little-endian faz com que cada byte do resultado 32-bit vire uma ativação separada. O byte 0 (LSB) geralmente é pequeno ou negativo, produzindo resultados incorretos. Este modo não serve como baseline de referência.

A terceira é no simulador C++, que processa 64 neurônios por iteração e descarta os intermediários — apenas o último grupo é salvo. O RTL real processa um neurônio por vez e escreve cada resultado individualmente.
